# SUPPLY REQUEST & INVENTORY MANAGEMENT SYSTEM

## 1. PROJECT OBJECTIVE

Build a lightweight, mobile-first web-based Supply Request and Inventory Management System for internal company use.

The purpose of the system is to allow employees to request office supplies through a web form accessed primarily by scanning a QR code.

The system must manage the complete lifecycle of a supply request:

REQUESTOR → APPROVER → RECEIVER → RELEASED

The system must also maintain office supply inventory and provide simple management metrics such as:

* Requests by department
* Requests by requestor
* Most requested supplies
* Supply consumption
* Request status
* Monthly request trends
* Low-stock supplies
* Out-of-stock supplies

The application must prioritize:

* Lightweight performance
* Low resource consumption
* Simple UI
* Mobile compatibility
* Easy maintenance
* Secure role-based access
* Clean database structure
* Vercel deployment
* Supabase backend

Do not over-engineer the application.

---

# 2. IMPORTANT DEVELOPMENT RULES

Before starting development:

1. Inspect the existing project structure if a project already exists.
2. Do not overwrite existing working functionality without understanding it first.
3. Do not install unnecessary dependencies.
4. Before installing ANY new dependency, ask the user for approval.
5. Explain why the dependency is needed before requesting installation.
6. Prefer native Next.js, React, TypeScript, Supabase, and browser APIs whenever possible.
7. Do not introduce a new library if the requirement can reasonably be implemented using the existing stack.
8. Keep the application lightweight.
9. Avoid unnecessary animations.
10. Avoid large image assets.
11. Avoid video backgrounds.
12. Avoid 3D graphics.
13. Avoid heavy dashboard effects.
14. Avoid unnecessary state-management libraries.
15. Do not use Redux unless explicitly requested.
16. Do not use Prisma unless explicitly requested.
17. Do not create a separate Express backend.
18. Do not create a separate Node.js server.
19. Do not use Docker unless explicitly requested.
20. Do not add unnecessary UI component libraries.

The final application should be optimized for low-spec office computers and low-to-mid-range mobile devices.

# 4. APPLICATION USER ROLES

There are four roles.

## ROLE 1 — REQUESTOR

The requestor is an employee who requests supplies.

Permissions:

* Login
* Create supply request
* Add multiple supply items
* Specify quantity
* Add purpose
* Add remarks
* Submit request
* View own requests
* View own request status
* View own request history

Requestors cannot:

* Approve requests
* Reject requests
* Modify inventory
* Release supplies
* View other employees' private requests unless explicitly permitted later

---

# ROLE 2 — APPROVER

The approver reviews requests.

Permissions:

* View pending requests
* View request details
* View requestor information
* View department
* View requested supplies
* View current inventory
* Approve request
* Partially approve quantities
* Reject request
* Add approval remarks
* View request history
* View inventory

The approver cannot directly release supplies.

---

# ROLE 3 — RECEIVER

The receiver handles the final release of supplies.

Permissions:

* View approved requests
* View request details
* View approved quantities
* View current inventory
* Approve/reject release
* Release supplies
* Add release remarks
* Confirm released quantity
* View release history
* View inventory

Inventory must only be deducted when the receiver confirms the actual release.

---

# ROLE 4 — ADMINISTRATOR

The administrator manages the system.

Permissions:

* Manage users
* Assign roles
* Manage departments
* Manage supplies
* Manage supply categories
* Add inventory
* Adjust inventory
* Set minimum stock levels
* View all requests
* View all inventory
* View analytics
* View audit logs
* Manage system configuration

The administrator should not normally be involved in the normal request approval workflow unless explicitly required.

# 11. INVENTORY RULE

This is critical.

Do NOT deduct inventory when the request is submitted.

Do NOT deduct inventory when the approver approves the request.

Only deduct inventory when the receiver confirms the actual release.

Example:

Current stock:

Ballpen = 150

Request:

10 Ballpens

Approver approves:

10

Inventory remains:

150

Receiver releases:

10

Inventory becomes:

140

Every inventory change must create an inventory transaction record.

* AI recommendations
* Real-time 3D dashboards
* Complex notification infrastructure
* Unnecessary microservices

Build the requested supply request → approval → release → inventory workflow first.

The system should remain small, fast, understandable, and easy for an internal IT team to maintain.

Final architecture:

GitHub
↓
Vercel
↓
Next.js

* VPS
* Docker
* Nginx

# 54. BEFORE IMPLEMENTATION

Before writing significant code:

1. Inspect the existing project.
2. Confirm the current Next.js/React/TypeScript setup.
3. Identify existing dependencies.
4. Identify dependencies that are already installed.
5. Propose the Supabase database schema.
6. Explain any dependencies that need to be installed.
7. Ask for confirmation before installing new dependencies.
8. Build incrementally by phase.
9. Test each phase before proceeding.
10. Do not silently introduce additional technologies.

When a requirement is ambiguous, stop and ask the user rather than making a major architectural assumption.

The goal is a **lightweight, secure, maintainable internal Supply Request and Inventory Management System**, not a complex enterprise platform.
